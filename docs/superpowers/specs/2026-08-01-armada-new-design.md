# armada new — best-practice repo generator (experience-aware)

Design spec. What it is, how it works, decisions. Also covers the `armada/` directory
consolidation and AGENTS.md merge behavior (design decisions discovered during planning).

---

## 0. armada/ directory — artifact consolidation

### 0.1 Motivation

Placing armada-owned files at the project root (`armada.yaml`, `REQUIREMENTS.md`) is
invasive. Users have their own root-level structure. Consolidating armada artifacts under
`armada/` keeps the root clean.

### 0.2 Target layout

```
project/
├── armada/
│   ├── armada.yaml              ← manifest (source of truth, always rewritten)
│   └── REQUIREMENTS.md          ← contract (default; configurable name/location)
├── opencode.json                ← opencode project config (root, opencode reads it)
├── AGENTS.md                    ← root (opencode reads it), merge behavior (see §0.3)
└── .opencode/                   ← opencode config dir (root, opencode reads it)
    ├── oh-my-opencode-slim.jsonc
    ├── oh-my-opencode-slim/
    └── commands/
```

### 0.3 AGENTS.md merge behavior

Current: no-clobber — skip writing if file exists.
New: marker-based merge.

- If `AGENTS.md` exists but has no `<!-- armada:start -->` marker: append armada section.
- If `AGENTS.md` exists with marker: replace the marked section on re-scaffold.
- If `AGENTS.md` absent: create full file.
- User-written content outside markers is never touched.

Marker format:
```markdown
<!-- armada:start -->
<!-- Generated by opencode-armada. Do not edit this section manually. -->
... armada team rules, role roster, defect ledger, phase gates ...
<!-- armada:end -->
```

All internal references update from `REQUIREMENTS.md` → `armada/REQUIREMENTS.md`.

### 0.4 Path changes throughout codebase

| Old path | New path |
|---|---|
| `armada.yaml` | `armada/armada.yaml` |
| `REQUIREMENTS.md` (default) | `armada/REQUIREMENTS.md` |
| `--from-armada armada.yaml` | `--from-armada armada/armada.yaml` |
| AGENTS.md references to REQUIREMENTS.md | `armada/REQUIREMENTS.md` |

`opencode.json`, `AGENTS.md`, and `.opencode/` stay at project root — opencode reads them
from there.

### 0.5 CLI flag preservation

`--from-armada` still accepts any path. The default changes from `armada.yaml` to
`armada/armada.yaml`. `--requirements <file>` can still override to any path.

## 1. What it is

`armada new [name]` creates a new project directory with an opinionated, curated scaffold
(starter templates + build configs + CI + README), then runs `armada init` inside to wire
up the multi-agent team. It is the "batteries included" cousin of `armada init` — `init`
requires an existing repo; `new` creates the repo first.

### 1.1 What it is NOT

- Not a replacement for `armada init`. `new` calls `init` as its final step.
- Not a generic scaffolding engine. Opinionated stacks with recommended defaults.
- Not a runtime dependency. Like `init`, `new` runs once.

## 2. Categories (v1)

| Category | Directory | Recommended stack |
|---|---|---|
| Web application | `starter/web-app/` | Next.js + Tailwind + TypeScript |
| ML model training | `starter/ml-training/` | Python + PyTorch + uv |
| Research paper | `starter/research-paper/` | LaTeX + Makefile + Zotero |

Each category has 2-4 curated stacks. The first is marked `recommended`.

---

## 3. Experience gate

**Detection heuristics** (run before the picker):

| Signal | Implies |
|---|---|
| `~/.gitconfig` exists | experienced |
| `node --version` succeeds | experienced |
| `python --version` succeeds | experienced |
| `~/.ssh/id_*` exists | experienced |
| Prior armada manifest found in `~/.armada/` | experienced |
| None of the above | beginner |

Detection is a hint. Always confirm with a yes/no prompt before proceeding.
Non-interactive flag `--beginner` / `--experienced` overrides.

## 4. Flow

### 4.1 Interactive

```
armada new my-app
  → "Which category?"
    1. Web application
    2. ML model training
    3. Research paper
  → Experience detection + confirm
  → Beginner path:
      "Pick a stack:"
      1. Next.js + Tailwind + TypeScript (Recommended)
      2. Remix + Tailwind + TypeScript
      3. Vue + Vite + TypeScript
      → scaffold from starter/<category>/<stack>
  → Experienced path:
      Drill-down per layer:
      - Frontend framework? [Next.js (Recommended) / Remix / Vue / None]
      - Backend? [Express (Recommended) / Fastify / FastAPI / None]
      - Database? [PostgreSQL (Recommended) / SQLite / MySQL / None]
      - Testing? [Playwright (Recommended) / Vitest / pytest / None]
      - CI? [GitHub Actions (Recommended) / None]
      - Deploy target? [Vercel (Recommended) / Docker / None]
      → scaffold from starter/<category>/default, layer overrides applied
  → Run armada init inside the scaffolded dir
```

### 4.2 Non-interactive

```
armada new my-app --type web-app --beginner   # recommended stack, no questions
armada new my-app --type web-app --yes         # recommended, experience auto-detected
armada new my-app --type ml-training --experienced  # drill-down, all questions
```

## 7. Integration with `armada init`

`armada new` finishes by calling the same `scaffold()` + `detectStack()` + `runQuestionnaire()`
functions that `armada init` uses:

```
new my-app --type web-app --beginner
  → mkdir my-app; cd my-app
  → copy starter/web-app/nextjs/, fill {placeholders}
  → armada init (programmatic, not subprocess)
     → detectStack(my-app) → { frontend: "nextjs", backend: "node", languages: ["typescript"] }
     → scaffold(manifest, stack)  → writes .opencode/, armada/, opencode.json, AGENTS.md
```

The init step uses the same `defaultManifest()` logic (balanced budget, all roles enabled,
no browser testing). Stack detection picks up what was scaffolded. User can re-run
`armada init` later to customize the team via questionnaire.

## 8. Experience detection implementation

```js
// src/new-command.js (or shared utility)
import { existsSync } from "node:fs"
import { homedir } from "node:os"
import { execSync } from "node:child_process"

export function detectExperience() {
  let score = 0
  const home = homedir()
  if (existsSync(`${home}/.gitconfig`)) score++
  if (existsSync(`${home}/.ssh/id_rsa`) || existsSync(`${home}/.ssh/id_ed25519`)) score++
  try { execSync("node --version", { stdio: "ignore" }); score++ } catch {}
  try { execSync("python3 --version", { stdio: "ignore" }); score++ } catch {}
  try { execSync("git --version", { stdio: "ignore" }); score++ } catch {}
  return score >= 2 ? "experienced" : "beginner"
}
```

## 9. Testing

### Catalog integrity (`tests/recommendations.test.js`)
- Every `CATEGORIES` entry has `label`, `stacks[]` (non-empty), and `layers`
- First stack in each array has `recommended: true`
- All `layers` keys are valid stack fields
- Every stack has `name`, `label`, `lang`, `deps`, `scripts`
- Placeholder consistency across template files

### CLI e2e (`tests/new-command.test.js`)
- `armada new my-app --type web-app --beginner` → output dir exists + `package.json` + `armada/armada.yaml`
- `armada new my-app --type web-app --yes` → same output, no interactive prompts
- `armada new` (no args, no TTY) → errors with usage
- `armada new --unknown-category` → errors gracefully
- Template renders fill all `{placeholders}` (no dangling braces in output)
- AGENTS.md merge: existing user content survives, armada section is appended/replaced

### Round-trip
- `armada new` → `armada init --from-armada armada/armada.yaml` → identical output

## 10. Non-goals (v1)

- No incremental adoption (converting existing repo to a starter template)
- No user-authored custom starter templates (only armada-maintained)
- No `armada new` inside an existing non-empty directory
- No post-scaffold database migration or seed generators
- No deployment (Vercel/GCP/AWS) auto-provisioning — only config files
